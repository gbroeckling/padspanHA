# PadSpan HA — Developer Notes (v0.4.14)

These notes are for future debugging sessions with ChatGPT / collaborators.

## What changed in v0.4.14

### 1) "All Objects" inventory + "Unidentified" list
- The Overview page now treats every metric as an entry point to a **list modal**.
- Buttons:
  - **All objects**
  - **Unidentified**
  - **Bluetooth radios**
  - **Rooms list**

The Objects modal shows a union of:
- **Entity objects** (Bermuda tags / device_trackers / etc. from the room map)
- **BLE objects** (unique BLE addresses deduped from HA Bluetooth advertisement monitor)

It includes:
- Filter box + kind/status dropdowns
- OUI frequency badge (≥3) — this is the "device type shows up more than twice" heuristic.
- Best-effort vendor lookup (online) with caching.

### 2) BLE snapshot is now included in `padspan_ha/live_snapshot`
`custom_components/padspan_ha/websocket.py` now injects:

- `snapshot.ble.radios`
- `snapshot.ble.advertisements`

This uses `BluetoothLive` (`custom_components/padspan_ha/bluetooth_live.py`) which subscribes to HA Bluetooth changes.

### 3) Device makers: built-in lists, nothing sent
`company_name` comes from the broadcast (`ble_enrichment.enrich_object`): the company number, then the company that holds a service UUID, then ESPresense's id (`apple:`, `msft:`, `tile:`, `md:`, `sd:`). An iBeacon's Apple number says nothing about its maker and is skipped.

The rest come from `apply_address_maker`, over the final object list:
- A radio confirmed the address public (`BluetoothLive.known_type`: ESPHome `details["address_type"]` 0 from firmware 2022.12 or newer, BlueZ `props["AddressType"]`, kept in `.storage` under `PUBLIC_ADDRESSES_STORE_KEY`): `company_name`, `maker_source` "address".
- A radio said random: never looked up. The type stays on the object (`address_type`) so history remembers it after the advert ages out.
- No word from a radio: `maker_guess`, shown as "Probably X". Bits 0x01 or 0x02 of the first byte mean IEEE didn't assign it, so those aren't tried.

The tables (`data/`, read by `device_tables.py`, off the event loop, once, on the first build) are generated by `tools/build_device_tables.py`: numbers and names only. Run it before a stable. Nothing in a release or a house asks IEEE or SIG for anything. The online lookup and its `vendor_lookup_enabled` setting are gone; `settings_store.RETIRED_SETTINGS` drops the setting and `async_setup_bluetooth_live` removes its old cache file.

A device's name, maker, type and how each is known come from `device_detail.py` (one function, `describe`), put on each object after the history merge, so never into history. `obj["name"]` is left alone because the same-name merge reads it. Screens read `best_name` through `www/padspan-ha/views/device_name.js`, which also gathers rotating addresses in lists. Calibration's saved labels deliberately still read `user_label || name`.

## Where to debug

### "Unidentified count is 0, but HA shows many ads"
- Confirm HA Bluetooth is enabled + you have scanners/proxies running.
- Check `snapshot.ble.advertisements` in the WS response for `padspan_ha/live_snapshot`.

### "Radios list shows the wrong devices"
- Radios are now taken from `snapshot.ble.radios` (not Bermuda / tag entities).

## Frontend pointers
- `www/panel.js` — adds modal helpers
- `www/views/overview.js` — Overview cards + list modals
