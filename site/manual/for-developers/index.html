Appendix D. For developers

Contents

How PadSpan is put together, the rules its code keeps, and every websocket command it registers. For contributing: the README's Development section. The longer design notes are in docs/ and are linked from each part.

The shape of it

PadSpan HA is one Home Assistant custom integration, custom_components/padspan_ha/:

  • The backend (Python): reads Home Assistant's Bluetooth data, ESPresense and Tasmota over MQTT, and the area, floor, device and entity registries; works out rooms and positions every poll (presence_coordinator.py); keeps its data in .storage/padspan_ha.* stores; creates the entities in sensor.py, binary_sensor.py, device_tracker.py and light.py; and answers the panel over Home Assistant's websocket.
  • The panel (plain JavaScript modules, no build step): www/padspan-ha/, with panel.js as the shell and one module per screen under views/. The sidebar Atlas is lights_panel.js.
  • PadSpan Bright is generated from the same source (scripts/bright_build.py), without the presence tracking.

A poll, in short: Bluetooth readings from every receiver → per-device smoothing over time → a room vote and, with three or more placed receivers, a position on the floor plan in metres → the entities and the live picture every open panel asks for.

The fabric

The metric fabric is the truth. Room shapes, receiver positions, signal walls, beacon pins and light positions live in metres, in the FabricStore (.storage/padspan_ha.fabric). A floor-plan picture is used to trace a building once and to look at afterwards. No working code may derive a position from a picture, its pixel size, a map's 0–1 fraction space, a map id or a per-picture transform. tests/test_photo_divorce.py holds this; three files remain quarantined (calibration.js, traceback.js, radio_map.js), and the guard fails if that list goes stale either way.

StoreFileOwns
FabricStorepadspan_ha.fabricRoom geometry, receiver, beacon and light positions, signal walls (all in metres)
ModelStorepadspan_ha.modelFloors, room metadata, adjacency, receiver room and floor, map transforms
MapsStorepadspan_ha.mapsThe floor-plan pictures and their metadata

Every write goes through a store method (ModelStore.async_remove_room, FabricStore.async_remove_room …), never through the stored blob: a handler that edits the data directly misses whatever has moved to the fabric since. A receiver's height (z_m) is measured from its own floor, never absolute. More: The mapping suite.

Cache busting

Home Assistant serves a custom panel's files with aggressive browser caching, so every panel file's address carries a stamp. A wrong stamp doesn't look like caching; it looks like your code not working.

SymbolWhereMeaning
BUILD_VERSIONbuild_info.pyThe version, shown in the sidebar and Diagnostics
BUILD_IDbuild_info.pyThe release stamp, rewritten by scripts/release.py
ASSET_IDbuild_info.pyBUILD_ID plus a digest of the frontend files: what addresses carry

build_info._frontend_digest() hashes every .js, .css and .html file's path, size and time under www/; panel.py registers the panel with ?v=<VERSION>&b=<ASSET_ID>; panel.js reads b off its own import.meta.url and uses it for every view it imports. So one stamp flows from the files on disk to every view, and moves whenever any frontend file does. A view imports another as await import(`./x.js${new URL(import.meta.url).search}`). More: UI cache busting.

RSSI vector capture

Capture records the input the positioning actually used (the full {receiver: rssi} reading per tracked device per poll) beside the answer it gave, so the same walk can be run again offline against changed code and the difference stated as a number. Off by default: Settings → Features → RSSI Vector Capture, then Health → ⏺ Record, Mark room in each room, ⏹ Stop and Export .jsonl.

  • Only named or followed devices are recorded.
  • A session stops itself at its duration (1 to 60 minutes), at 25 MB, or when the integration unloads.
  • tests/test_capture_replay.py has load_capture() and replay(): a golden regression (the replayed room equals the recorded one) and an accuracy score against the rooms you marked.
  • The accuracy benchmark tools read the same files: appendix C.

More: RSSI vector capture.

Hard-won rules

Each came from a real mistake; the full text with the story is in Hard-won rules.

  1. A frontend change you can't see is not a frontend change.
  2. node --check doesn't run the code.
  3. Look at it rendered.
  4. The fabric is the truth, and every write goes through its store.
  5. A sidecar that nothing fills is worse than no sidecar.
  6. An index difference that means something must be computed that way.
  7. Guards that list their targets by hand go stale.
  8. A fixture that can't fail is worse than no fixture.
  9. Record what the pipeline used, not what it produced.
  10. Test it against the site it will run on.
  11. Deploy, restart, and click the button.
  12. Two views that draw one thing must share a contract, not a guess.
  13. When something "no longer works", check what it is still reading.

Working in the repository

  • Several sessions often work at once: each in its own worktree and branch. Release notes are files in changelog.d/, never a section written into CHANGELOG.md by hand. Releases go through scripts/release.py only. The repository's CLAUDE.md has the rules.
  • A new third-party import goes into requirements_test.txt in the same commit (tests/test_requirements_declared.py).
  • Names from devices, receivers and rooms are always set as text, never as markup (tests/test_hostile_names.py).
  • PadSpan never changes another integration's devices or entities on its own; a test fails if new code tries to.
  • The manual's reference tables (chapters 12, 14, 20 and the table below) are made by scripts/build_manual_reference.py and pinned by tests/test_manual_reference.py. When that test fails, run the script and commit what it wrote.

Websocket commands

Every command the integration registers, read from the code: each handler with @websocket_command that the integration registers. Administrator says always for a handler marked require_admin, and with Enhanced security for one that needs an administrator while Enhanced security is on (chapter 21). A handler can also refuse parts of a request inside it. These are the panel's own commands, not a stable public interface: they change between versions. For automations, use the entities, services and events in chapter 14. More: Websocket API.
